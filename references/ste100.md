# STE-lite: controlled language for explanations

ASD-STE100 (Simplified Technical English) is a controlled language developed for aerospace maintenance documentation. It combines a restricted dictionary of approved words with strict writing rules. The current issue of the standard is copyrighted; this file is a working summary for explanations, not a replacement for the specification.

Use this guide when clarity, consistency, and translatability matter more than literary style: procedures, policies, safety notes, onboarding, audit findings, and technical explanations.

## Two modes

### Full STE

Use full STE when the user asks for ASD-STE100 compliance or when the document will be used for maintenance, safety, or regulated procedures. Full STE requires the approved dictionary and the current rule set. Do not claim compliance unless you have checked the actual standard.

### STE-lite (default: about 80% of the way)

Keep the structural discipline. Relax the dictionary enough to preserve precise technical terms and natural phrasing.

Keep:

- short sentences;
- active voice;
- one term for one thing;
- one instruction per sentence;
- explicit subjects and articles;
- warnings before the step;
- vertical lists for procedures;
- consistent units, abbreviations, and formats.

Relax:

- the approved-word dictionary;
- the strict limit on every descriptive sentence;
- the ban on all natural phrasing.

Never relax:

- factual accuracy;
- the meaning of a technical term;
- the order of a procedure;
- a warning or prerequisite.

## Working rules

### Sentences

- Put one idea in each sentence.
- Keep instructions at 20 words or fewer. Keep descriptions at 25 words or fewer. Split instead of compressing.
- Use active voice. "The parser rejects the token" is clearer than "The token is rejected by the parser."
- Use the imperative for steps: "Open the valve." Not "The valve should be opened."
- Use simple present for general facts. Use simple past for events that happened.
- Avoid contractions: write "do not", not "don't".
- Avoid semicolons. Write two sentences.
- Avoid parenthetical asides when the information is necessary. Make it a sentence.
- Avoid "-ing" clauses that hide the actor: "After opening the valve, check the pressure" -> "Open the valve. Then check the pressure."

### Words

- Use one term for one concept. Do not rotate synonyms for style.
- Define a term the first time it appears. Add a glossary if the document is long.
- Use "must" for a requirement, "can" for a capability, and "will" for a future event.
- Avoid "should", "may", "might", and "could" when they make a requirement ambiguous. Replace them with a clear condition or a direct instruction.
- Avoid idioms, metaphors, jokes, and cultural references.
- Avoid vague words: "etc.", "and so on", "and/or", "several", "appropriate", "as needed" without a condition.
- Avoid noun clusters of four or more words. "Server configuration validation procedure" -> "procedure to validate the server configuration".
- Keep articles. Do not write telegraphic English.
- Spell out an abbreviation on first use. Use the abbreviation consistently after that.
- Use consistent units and number formats.

### Structure

- Start with purpose: what the document helps the reader do.
- State the audience and required knowledge.
- List prerequisites before the steps.
- Put warnings before the step they apply to. Use a consistent label such as **WARNING**.
- Use a vertical list for three or more steps or conditions.
- Keep one topic per paragraph. Aim for six sentences or fewer.
- End with verification: how the reader knows the task worked.
- Put sources and open questions at the end.

## Before and after

**Before:** "In order to ensure that the system is able to efficiently process incoming requests, it is important that the configuration is validated prior to initiating the deployment procedure."

**After:** "Validate the configuration before you start the deployment. A valid configuration lets the system process requests without errors."

**Before:** "The utilization of a cache can result in a reduction in latency."

**After:** "A cache can decrease latency."

**Before:** "The model leverages attention mechanisms to aggregate contextual information from neighboring tokens."

**After:** "The model uses attention to combine information from neighboring tokens. Attention lets each token use context from other tokens."

**Before:** "If the request fails, the operator should check the logs and possibly retry, and if the problem persists, they may need to escalate the issue."

**After:** "If the request fails, check the logs. Then retry the request. If the request still fails, escalate the issue."

## Procedure pattern

```markdown
# <Task>

## Purpose
This procedure shows you how to <result>.

## Audience
You need <knowledge> and <access>.

## Before you start
- <prerequisite>
- <required tool or permission>

## Terms
| Term | Meaning |
| --- | --- |
| <term> | <one-sentence definition> |

## Steps
1. <One action. One sentence.>
2. <One action. One sentence.>
3. <One action. One sentence.>

## Warning
<What can go wrong. What to do instead.>

## Verify
<How to confirm the result.>

## Sources
- <source and anchor>
```

## Prompt template

```text
Rewrite the text below in 80% ASD-STE100 style.

Rules:
- Keep every fact, number, name, unit, and technical term.
- Use short sentences: 20 words or fewer for instructions, 25 or fewer for description.
- Use active voice and simple present.
- Use one term for one concept. Do not add synonyms.
- Use one instruction per sentence. Use a numbered list for steps.
- Put warnings before the step they apply to.
- Remove contractions, idioms, semicolons, and vague words.
- Do not add facts, examples, or conclusions that are not in the source.
- If the source is ambiguous, keep the ambiguity and add a note after the rewrite.

Output:
1. The rewritten text.
2. A short list of changes.
3. A list of ambiguities or terms that need a definition.

Text:
<source text>
```

## Heuristic lint

Run:

```bash
python3 scripts/ste_lint.py document.md --max-sentence 20 --max-cjk 60
```

The linter checks sentence length, contractions, common wordy phrases, semicolons, vague words, possible passive voice, and long paragraphs. It is a heuristic. It cannot check the approved dictionary, technical accuracy, or whether a sentence has one instruction. Treat its output as a review queue, not a compliance certificate.

Use `--fail-on warning` in a quality gate. Use `--json` for tooling.

## Limits

- STE was designed for maintenance documentation, not for marketing, narrative, or exploratory writing.
- Strict STE can make a nuanced argument sound more certain than it is. Use STE-lite for explanations where uncertainty matters.
- A controlled vocabulary can hide a missing definition. Always define the terms the reader needs.
- Do not claim ASD-STE100 compliance unless you have checked the current standard and the approved dictionary.
